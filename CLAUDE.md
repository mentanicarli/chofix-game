# CLAUDE.md — Cuppable

Контекст проекта для Claude Code. Читай целиком перед любой работой. Язык общения с владельцем и весь текст в игре — **русский**. Код и идентификаторы — английские, комментарии — русские, как в существующих файлах.

## Что это

**Cuppable** (раньше Chofix) — браузерный симулятор кофейни в университете («кофе между парами»). Бариста от первого лица за баром, зал с гостями, HUD, тикет, книга рецептов, магазин улучшений, дни и ранги. Стиль: **плоский тёплый минимализм**, рисованные контуры цвета `#4A2F25`, тёплая бумажная фактура.

Результат сборки — **один самодостаточный `dist/artifact.html`** (всё встроено: JS, CSS, SVG-арт). Раньше игра жила как артефакт на claude.ai (`https://claude.ai/artifact/Es81JMU7dGQDjXLUsPmBWp`, версия 22 на момент передачи проекта). Дальше разработка идёт локально; публикация в артефакт — отдельное решение владельца.

Звуки (`public/sfx/*.webm` + `manifest.json`) грузятся по относительному пути `sfx/…` рядом с html. В одиночном `dist/artifact.html` их нет — для звука отдавай `dist/` целиком (`npm run dev` или любой статический сервер).

## Жёсткие правила (владелец их подтверждал)

1. **Игра для игрока не меняется при технических переделках**: баланс, цены, ощущение управления, тайминги, внешний вид. Любое расхождение при рефакторинге — баг. Исключение — то, что владелец явно просит изменить.
2. Логика в `src/game/*` — чистая: **ничего про DOM, window, localStorage, Pixi** (запрещено линтером). Формулы закрыты тестами.
3. TypeScript strict, без `any` и без `!` (для `src/render/world/**` `no-non-null-assertion` отключён осознанно).
4. Любой шаг заканчивается зелёным `npm run check` (+ `npm run lint:legacy`) и прогоном игры на реальных событиях мыши (см. «Проверка»).
5. Не публиковать и не считать работу законченной, пока не проверено глазами (скриншот) и тестом. Версия 20 однажды была выпущена со сломанным залом — потому что скриншот посмотрели невнимательно. **Всегда смотри скриншот после изменений рендера.**
6. Честно отчитываться: что проверено, а что нет (реальная видеокарта, звук на хостинге и т. д. сюда не входят).
7. Текст для игрока: простой язык, предложения с заглавной, кнопка называется тем же словом, что и результат действия.

## Стек и архитектура

- Vite 8 + TypeScript 6 (strict) + Pixi.js 8 + vitest 5 + eslint. Сборка в один файл: `vite-plugin-singlefile` + `scripts/fragment.mjs`.
- «Всё в Pixi» для мира, HTML/CSS для интерфейса:
  - **Pixi (холст `#world`, 1280×720 логических пикселей):** зал, гости, барист, лампы/небо/свет, **сцена бара от первого лица**, частицы (монеты, пар, искры). Инсеты станций (помол, темпер, шот, вода, молоко, пар, заливка/латте-арт, сироп) — в отдельном Pixi-холсте `#bp` (`src/render/*`, `inset.ts`).
  - **HTML/CSS поверх:** HUD, тикет заказа (`#bTk`), коуч-подсказки, панели «нового ядра» станций (`#xPanel`: whisk/brew/juice/tonic/powder/boba/topping/blend/shake/foam/whip/layer), панель еды, книга рецептов, магазин, тосты, экраны итогов, реплика гостя (`.say`), кликабельные зоны бара (`#bZones` — прозрачный SVG поверх холста).
- Старое ядро игры — **`src/legacy/NN-*.js`**: куски склеиваются плагином `cuppable-legacy` из `vite.config.js` в один IIFE по номерам (общая область видимости, без импортов между кусками). Это живой код, а не «мусор»: цикл игры, дни, клиенты, бар, экраны. Он **не линтится обычным eslint** (только `npm run lint:legacy` ловит неопределённые имена). Новую логику выноси в `src/game/*` (чистые модули) и вызывай из legacy через `MENUAPI` (`src/game/api.ts`).
- Чистая логика (`src/game/`): `menu`, `volumes` (объёмы, шоты, пена, зоны пара, масштаб чашки: `recipeNumbers`), `recipeCard` (карточка рецепта для бара и книги), `orders` (генерация заказа), `phrases`, `economy` (цены, себестоимость по объёмам `recipeCost`, аренда, итоги дня `settleDay`), `shift`, `quality`, `save`, `food`, `helper` (помощник), `settings` (настройки игрока: разбор, границы, `isLowGraphics`), `recipes` + `stations/*` (универсальная система рецептов: задачи `buildTasks` по `data/menu.json`).
- UI-модули на TS: `src/ui/book.ts` (книга рецептов), `foodPanel.ts`, `stationPanel.ts`, `menus.ts` (разметка меню, настроек, паузы, подтверждений), `music.ts` (плеер на `HTMLAudioElement`: случайный порядок, кроссфейд, предзагрузка).
- **Меню и настройки:** `#screen` показывает один экран; корень меню помечен `data-menu="title|pace|howto|settings|confirm|pause"` — по нему `menuView()` понимает, что открыто (Esc, клавиша P). Настройки — отдельный ключ `chofix-settings` (`SETTINGS_STORE` в `10-save.js`), применяются сразу через `applySettings()`. Сохранение игры — через `SAVE_STORE` (`load/save/clear`, сейчас localStorage; сюда подключаются аккаунты), формат версионируется (`SAVE_VERSION`, `readSave` мигрирует v1). Сохраняется состояние **на начало дня** (автосейв в `startDay`, после покупки, в конце дня); «В главное меню» посреди дня день не сохраняет — иначе деньги смены можно было бы перепройти.
- **Магазин: показывается только то, что даёт эффект сразу** (`src/game/shop.ts`, `isShopItemAvailable(item, {rank, owned})`; экран — `showEvening` в `11-screens.js`, состояние — `shopState()`). Не серая и не заблокированная карточка, а скрытая. Условия: «Молоко и капучино» — ранг ≥ `MILK_RANK` (минимальный `rank` среди напитков с молоком); «Трафарет для арта» и «Питчер с термометром» — только когда куплено молоко; `eq_*` — ранг ≥ `rank` оборудования в `progression.json` и есть открытый по рангу напиток (или блюдо), которому оно нужно, при этом всё остальное оборудование и молоко этого напитка уже куплены (так сифон ждёт льдогенератор, порошки/матча/пенка — молоко, микроволновка — купленную витрину с разогреваемым блюдом); зерно, кофемолка с экраном, темпер, кофемашина Pro, зал, Wi-Fi, карта и помощник показываются всегда со своими `minDay`/`minRank` (кнопка «С дня 2», «Ранг 5»). Купленное остаётся (штамп «Куплено»), сохранения не трогаются. При повышении ранга плашка вечера (`.rankcard.up`, `s.shopNew`) пишет «В магазине теперь можно купить: …», после покупки — плашка `G.buyNote` с тем же текстом (`newlyAvailable`, `shopNewText`). В книге рецептов «Нужно купить» называет цену только у того, что уже есть в магазине, остальное — «Потом в магазине появится: …». **Гарантия отдачи:** покупка кладётся в `G.fresh` (в сейв не пишется), `startDay` переносит её в `D.focus`; `spawn` (`04-customers.js`) передаёт `focus` в `rollOrder`, когда осталось ровно столько гостей из первых пяти, сколько неиспользованных покупок (`orderUsesItem`, `drinkFitsItem`, `forceFood`). Без `focus` заказы считаются как раньше (тест на равенство).
- **Подсказки новых станций:** `src/game/tutorial.ts` — по 1–2 шага на оборудование (`TUTORIALS`), `tutorialEqs(task, food)` (шаг бара → оборудование), `purchaseToast`. В баре `tutEq()`/`tutText()` (`08-bar-view.js`): пока станция не пройдена (`G.tutorialSeen`, пишется в сохранение), коуч вместо обычной подсказки ведёт по её шагам, даже если «с 3-го дня» подсказки погасли сами; не показывается, если игрок выключил подсказки (настройка или «?» → `G.tutOff`). Метка ставится в `complete()`. При покупке в магазине наверху вечернего экрана жёлтая плашка «Новое: …» (`G.buyNote`). В книге рецептов у карточки напитка кнопка «Подсказка» раскрывает тот же текст, а «Нужно купить» показывает цены. Сценарии: `e2e/tutorial_flow.js` (матча), `e2e/book_tut.js`.
- **Обучение по шагам и «Новый напиток»** (`src/game/lessons.ts`; в баре — `tutKey/tutText/tutHl` в `08-bar-view.js`, карточка — `showDrinkCard` в `06-bar.js`, DOM `#drinkCard`, подсветка кнопки окна станции — `#tutHl`). В `tutorialSeen` лежат строки: станция (`matcha`), карточка напитка (`drink:latte`), шаг (`step:milk`, `step:steam:thick|thin|micro`, `step:pour`, `step:syrup`) и метка `v2`. `migrateSeen` один раз переносит старое сохранение без метки (напитки прошлых рангов, молоко/пар при купленном молоке считаются пройденными); новая игра стартует с `freshSeen()`. При первом заказе напитка перед приготовлением — карточка с рецептом (те же шаги, что в книге) и «Понятно» (Пробел/Enter/Esc тоже закрывают; терпение гостей и таймер дня на это время стоят). Дальше `nextTutorial(task, drinkId, food, seen)` ведёт по шагам: коуч показывает один текущий шаг (`lessonStep` по живым числам: молоко до линии → «Готово»; воздух → закрутить → остановить по термометру), подсвечивает кнопку и зону, у коуча есть «Пропустить»; отметка ставится в `complete()`. Выключены подсказки (настройка или «?») — карточек и шагов нет. Числа пара (`STEAM`: 7°/с, пена 0,2/с у поверхности пока молоко холоднее 46°, пригорает с 76°, зона по напиткам `steamZoneOf` (см. «Рецептуры и объёмы»), с термометром −2/+3°) живут в `lessons.ts` и используются симуляцией (`07-bar-sim.js`) — менять только там. Виды пены: густая (капучино, 0,55), лёгкая (латте и остальные молочные, 0,22), микро (флэт уайт, 0,11); у рафа 0,33 при виде «лёгкая» (цель берётся из рецепта). Новые подсказки по шагам: `step:shots` (несколько шотов, показывается на первом помоле) и `step:pitcher` (эспрессо в питчер у рафа). «Как играть» → «Показать подсказки заново» сбрасывает `tutorialSeen` в сохранении. Сценарий: `e2e/milk_flow.js`; после первого `Space` на заказе тесты вызывают `require('./pw').dismissCard(p)`.
- **Тексты К1 в игре (К2).** Источник правды — `docs/content/*.md` (`drinks.md`, `guide.md`). `npm run content` (`scripts/make-content.mjs`) разбирает их в **`src/game/content/generated.ts`** (коммитится; `npm run content:check` сверяет без записи и входит в `npm run check`): на напиток — «Что это», шаги без цифр, «Если со льдом» (только у семи с холодной механикой), «Чем отличается», «Размеры», «Картинка» (поле для этапа Н, в игре не показывается); справочник (`GLOSSARY`), экраны «Зачем» (`WHY_TEXTS`), список станций (`STATION_NAMES`). «Точные цифры» и «Проверить» в игру не попадают: цифры всегда из `recipeCard`. Тексты правим только в md и пересобираем. Тест `test/content.test.ts`: 37 напитков, пустых полей нет, нет «слева/справа/сверху/…» и «!», названия станций из списка. Книга (`book.ts`): один рецепт на напиток, переключатели размера и «Горячий/Холодный» (`data-booksize`, `data-bookcold`; состояние `bookSel` в `11-screens.js`), блок «Точные цифры» по умолчанию закрыт (`data-bookexact`, `bookExact`), пустой слот картинки `.imgSlot` (скрыт, этап Н), вкладка «Справочник» (термины `<details>`, поиск по названию `data-guideq`). Карточка «Новый напиток» (`newDrinkCard`: `what/steps/ice/differs/exact`) и окно «Зачем это нужно» (`showWhy`) используют один `#drinkCard` и `CARDON` (таймеры, терпение и симуляция бара стоят, Пробел/Enter/Esc закрывают). **Ключи `why:*` в `tutorialSeen`** (`src/game/why.ts`): станция — при первом открытии окна (`openInset` → `whyOfInset`), механика — при заказе (`whyOfOrder`: сливки раф, два шота, слои, топпинг, другой вид пены); `orderIntro` ставит «Зачем» перед карточкой, по одному окну за раз. Метка `v3` (`WHY_MARK`): сохранение без неё переносит `migrateSeen` — всё открытое рангом или купленное (`whySeenOf`) считается виденным, новая игра (`freshSeen`) стартует без `why:*`; «Показать подсказки заново» сбрасывает и их. `why:sections` («Как листать бар», `WHY_SECTIONS`) — экран листания секций бара: текст в guide.md, показ и условия в «Подсказки секций (Б1-3)». Подсказки (`tutorial.ts`, `lessons.ts`, коуч в `08-bar-view.js`) называют станции по именам из `guide.md` и не содержат положений на экране и цифр (цифры остались на индикаторах и в «Точных цифрах»). `dismissCard` в `e2e/pw.js` закрывает все окна подряд; сценарий `e2e/content_flow.js`.
- **Музыка:** `public/music/*.mp3` + `public/music/manifest.json` (генерирует `scripts/make-music-manifest.mjs`, запускается из `predev`/`prebuild`, в git не лежит). Названия: ID3 → имя файла «Исполнитель - Название.mp3» → имя файла. mp3 в git кладём, но только с правами на использование. **Порядок случайный** (`src/game/playlist.ts`: `shuffleOrder` — Фишер—Йетс с `rng`, `Playlist`): на каждом запуске новая перестановка, круг = все треки по разу, последний трек круга не открывает следующий; порядок нигде не хранится. Кнопок «следующий/предыдущий» нет. «Сейчас играет» показывает только название (без исполнителя). Нет треков — ползунок и строка «сейчас играет» скрыты. Лёгкая графика (`World.setLowFx`): без частиц, ореолов ламп, пятен света и луча, разрешение ≤ 1.

### Песочница разработчика (`#dev`)

Ссылка с хешем `#dev` (с другими через дефис: `#dev-nopixi-lowfx`) включает песочницу; без него `DEV` в `00-core.js` ложь, `SBX.on` ложь и все хуки нейтральны (игра бит-в-бит прежняя). **Принцип: день определяет состояние.** Игрок выбирает день и профиль («Средний»/«Уверенный»), остальное выводится так, чтобы состояние было достижимо для обычного игрока: ранг, рейтинг, «обслужено», деньги — из `data/typical-progress.json` (медианы модели игрока `src/game/playerModel.ts` по 60 прогонам; генерация `npm run sim:table`, в `check` не входит, JSON в git; перегенерировать после изменения цен, порогов рангов, правил магазина/`SHOP_BASE`, экономики и прихода гостей или модели); ранг ≤ `maxRankForDay(день)` (`minDay` и потолок «обслужено» профиля «Уверенный»), рейтинг и «обслужено» не ниже порогов ранга. Покупки: режим «Всё доступное» (по умолчанию; `allAvailableItems` — неподвижная точка `isShopItemAvailable` + «С дня»/«Ранг», цепочки зависимостей) или «Как у типичного игрока» (покупки из таблицы, пропущенные через `sanitizeItems`); день 1 — ничего. Блок «Своё» (`config.custom`) позволяет править ранг, рейтинг, «обслужено», деньги и позиции, но всё приводится к допустимому для дня (`resolveSandbox`); недоступные позиции на экране выключены. Чистая часть — `src/game/sandbox.ts` (`resolveSandbox`, `makeSandboxState(config)`, `seenFor` — обучение только по виденному, `summarizeShift`, ключ `chofix.sandbox.v1`), разметка — `src/ui/sandbox.ts`, обработчики — `src/legacy/16-sandbox.js` (в нём только объявления, исполняемый код под `if (DEV)`). Панель во время смены: «DEV» с заголовком «День N · ранг R · режим», скорость времени, «Закончить день», деньги/рейтинг/«Следующий ранг» (в режиме «Всё доступное» открывает ставшие доступными позиции; выше допустимого для дня — тост «Для этого дня ранг нереалистичен», действие всё равно выполняется), «Позвать гостя», «Без терпения», тип гостя и частота, подмена следующего заказа, неограниченные деньги, бесплатные ингредиенты, статистика смены с «Скопировать JSON». Хуки в обычном коде, все по умолчанию ничего не меняют: `rollOrder(state.override)` (`OrderOverride`), `SBX.scale`/`rate`/`noPat`/`type`/`next` в `tickDay`, `interval`, `spawn`; `spend(n)` вместо прямых `G.money -= cost`. **Настоящий сейв песочница не читает и не пишет:** при `SBX.on` методы `SAVE_STORE` (`load/save/clear/quarantine`) ничего не делают; настройки игрока не меняются. Выход в меню (`showTitle`) выключает песочницу. Для e2e: `require('./pw').sandboxStart(p, url, { day, profile, mode, custom })` (запускает `window.__sandbox.start` — тот же код, что у кнопки «Начать»); особое оборудование для сценария задавать `custom` с комментарием; пример — `e2e/sandbox_flow.js`. Список позиций магазина `SHOP_BASE` (`playerModel.ts`: id, цены, `minDay`/`minRank`) обязан совпадать с `SHOP` в `00-core.js` (сверяет тест).

### Мир на Pixi — `src/render/world/`

- `world.ts` — класс `World`: инициализация (`init`), слои, `update(dt, k, minutes)`, `render(dt, frameMs)`, API для legacy: `setMenu`, `setUpgrades`, `setBarista`, `baristaJoy`, `setHeld`, `addActor/removeActor/clearActors`, `setBar(on)`, `paintBar(frame)`, `setBarUpgrades`. Внутри два слоя одного холста: `hall` (зал) и `bar.root` (бар); вход в бар — плавное наложение (0,3 с), в конце зал скрывается.
- `art.ts` — палитры, внешности гостей (`LOOKS`, `lookFor`), `personParts` (ноги/торс/руки/голова — отдельные растровые части, `PERSON_BOX`), части баристы.
- `actor.ts` — гость/сидящий: ригинг частей, дыхание, моргание, пузырь заказа с полоской терпения, тряска, `setSeated`.
- `bar.ts` — сцена бара: статичный арт одним спрайтом + подвижные детали (портафильтр, слои жидкости в чашке с маской, струя, пар, стрелка манометра, питчер, звонок, кольцо подсказки). Данные частей генерируются из SVG в `src/assets/art/bar-parts.json`.
- `fx.ts` — частицы. `svg.ts` — растеризация SVG-кусков в текстуры (`raster`, `bakePaper`).
- Арт: `src/assets/art/*.svgf` (куски SVG, общие градиенты и фильтры в `defs.svgf`) и `bar-parts.json`.
- Текст в Pixi — нативный `Text` (SVG-в-картинке не видит веб-шрифты Caveat/Nunito); шрифты догружаются через `document.fonts.load` с кириллическим образцом.
- Бумажная фактура запечена в один слой «цвет+альфа» (`bakePaper`); поверх всего ещё DOM-слой `#tint` (multiply), он тонирует и бар, и HUD.
- Разрешение: `clamp(dpr·stageScale, 1, 2)`. На **программном WebGL (SwiftShader и т. п.)** включается половинное разрешение и адаптивный интервал отрисовки. Хэши адреса для автотестов: `#lowfx` (рисовать раз в 0,4 с), `#nofx` (не рисовать), `#nopixi` (инсеты на старом canvas 2D), `#pixi` (принудительно Pixi для инсетов).
- Гость за столиком (`stepSitter` в `world.ts`): приходит слева, садится с ноутбуком, пьёт кофе, через 30–60 с уходит, через 4–12 с приходит другой. Чисто декоративный, в логику игры не входит.

**Масштаб гостей.** Верх стойки (y 399) был на уровне головы гостя (205 px от пола y 600 до макушки), теперь гости выросли в `GUEST_K` = 1,6 (`art.ts`) от точки на полу, и стойка приходится на ~61 % их роста. Ходячие: `Actor.root.scale` (pivot (0, 600) = ноги), скорость для шага/наклона делится на `k`, прыжок, покачивание и «опорная ступня» умножаются на `k`, пузырь заказа масштабируется `s / k` (размер прежний, хвостик у макушки), атлас растеризуется с `res · k`. Сидящий: растут вместе `sitC`, `tableC` и `deskC` от `SEAT_PIVOT` (230, 652), поэтому внутри них все координаты (ноутбук, блюдце, чашка `tableCup`, стул) остались «исходными»; маски `seatMaskA/B` лежат вне дерева, их прямоугольники переводятся той же формулой (`mx/my` в `seatMasks`) — менять только вместе с `GUEST_K`. Для эффектов на госте в legacy: `gx(c, dx)`/`gy(y)` (`04-customers.js`), `WORLD.guestK`; реплика `.say` — `top: 24px`, над пузырём заказа; очередь `SLOTS` = 640/510/380 (шире, чтобы выросшие гости не слипались).

Слой 11: на `sitFront` (руки и чашка сидящего) такая же маска `seatMaskB`; когда гость тянется к чашке справа (`Actor.reaching`), её правый край отодвигается до края крышки, и рука видна справа от ноутбука. В маске `seatMaskB` есть окно под чашку на блюдце (x от 270, y 524–546): раньше правый край маски (x 284) обрезал левую часть чашки, а на её месте проступала столешница.

**Фокус:** кольцо фокуса рисуется только при `html.kbd` (включается по Tab или стрелкам, выключается любым нажатием мыши или касанием, `11-screens.js`), поэтому программный `.focus()` в меню и паузе кольца не даёт. Новые правила `:focus-visible` писать как `html.kbd …:focus-visible`.

DOM поверх холста: `#bar` (z-index 2: тикет, коуч, инсет, панели) < `#screen` (z-index 10: титул, пауза, настройки, итоги) < `#boot` (30). Пока игра на паузе, `#stage.paused` скрывает (`visibility`) `#bar`, `.say`, тосты, плашки; правило лежит в конце `bar.css`, чтобы перебить `#stage.inbar #bar`.

**Пауза** (`setPause` в `15-menu.js`): `paused = true` замораживает цикл (`tickDay`, `animActors`, `barTick`), `pauseFreeze()` отпускает зажатое (`BR.hold = false`) без оценки шага; все обработчики бара (`#bZones`, тикет, `#bClose`, `bi`, панели) возвращаются при `paused`. Автопауза: `visibilitychange` и `blur`. Корень старой ошибки: `#bar` (z-index 2) лежал выше `#screen`, поэтому клики по «Продолжить» попадали в прозрачные зоны бара. Проверка: `e2e/pause_test.js`.

### Зоны бара (`#bZones`)

Правило: **зона активна, только если то, что в ней, нарисовано на баре.** `zoneShown(z)` в `06-bar.js` (те же условия, что `WORLD.setBarUpgrades`: `milk` — `G.milk` (холодильник с молоком), `ice` — `eq_ice`; `food` — любая витрина/холодильник с едой; `tea…shaker` — `eq_<id>`; остальные зоны — часть статичного арта, всегда активны). `zonesSync()` (зовут `applyUpgrades` и `barShow(true)`) ставит `pointer-events:none` на неактивные `rect[data-z]` — ни курсора, ни подсказки, ни звука; `zoneClick` дополнительно возвращается для них (тикет, Пробел). «X не нужен» — только для оборудования, которое есть на баре. Холодильник с молоком — отдельная часть `milk` в `bar-parts.json` (корпус, содержимое, ручка, подпись «молоко», кусок края полки сиропов, который он перекрывает), её показывает флаг `milk` в `setBarUpgrades`; без молока на этом месте в статике нарисована пустая стена с полкой (растение и кружки), поэтому зона молока до покупки не принимает клики, а после покупки (`applyUpgrades`) включается сразу. ## Рецептуры и объёмы (`src/game/volumes.ts`, `recipeCard.ts`)

**Единый источник чисел:** `recipeNumbers(drink, size, cold)` в `volumes.ts` — состав, цели налива, шоты, пена, зона пара, объём чашки. Из неё берут бар (`legacyRecipe`, `taskTarget` в `recipes.ts`), книга рецептов (`recipeCard` → `src/ui/book.ts`), себестоимость (`recipeCost`) и заказы. Нигде больше цифры объёмов не хранятся. Шаги и порядок — `data/build_menu.py` (`steps`, поле `shots`) → `menu.json`, шаги заказа собирает `buildTasks`.

- Размер в литрах = объём напитка V (мл). Шоты по размеру `SHOTS_BY_SIZE` 1/1/2/2; шот 30 мл, доза около 9 г (весы бара в условных единицах: 2 на грамм, цель 18 = 9 г, крепкий 20 = 10 г и 25 мл). Вода/молоко = V − 30·S. «Эспрессо» (ключ механики `espresso`, чашка 90 мл) и «Двойной эспрессо» (ключ `espresso2`, чашка 120 мл, два шота) — отдельные позиции, флэт уайт всегда два шота (`Drink.shots`: число или `'size'`).
- Молоко до пара = M / (1 + x), `FOAM_X` (капучино 0,5, латте 0,2, флэт уайт 0,1, раф 0,3); шкала «Пена» в баре = x · 1,1 (`foamTarget`). Зоны пара по напиткам `STEAM_ZONES` (капучино 60–65, латте 55–62, флэт уайт 55–60, раф и какао 60–65), термометр: −2/+3°. Кривую пара (`STEAM` в `lessons.ts`) не трогать.
- Холодные: жидкость 0,55·V, лёд 0,3·V (занимает 0,45·V, `ICE_G_PER_ML`), размеры 0,3/0,4/0,6. Сироп из рецепта: 8 мл на помпу, помпы 2/3/4/5, его объём вычитается из главной жидкости. Главная жидкость (молоко, лёд у фраппе) «добирает» объём до V, чтобы сумма составляющих сходилась с допуском 3% (тест `volumes.test.ts`).
- **Шаг «лёд»** (`buildTasks`, `recipes.ts`): в конец холодного заказа добавляется, только если у холодного рецепта есть цель льда (`hasIceTarget`, `recipeNumbers.ice > 0`) или напиток «и горячий, и холодный»; протеин (`protein_milk`, `protein_water`) готовится без льда (раньше шаг добавлялся без цели, бар ждал лёд, которого нет). Тест `test/iceStep.test.ts`; известное расхождение (шаг «лёд» есть, цели нет) осталось у холодных вариантов десяти «двойных» напитков без холодной механики (только книга и окно), список зафиксирован в тесте. `bar_test2.js` падает, если встретит шаг «лёд» без цели.
- **Раф** — классика: эспрессо сразу в питчер (`pitcherShot`, `BR.pit.es`), сливки (шаг `milk`, подпись «Сливки»), сироп (после сливок) или сахар, пар, заливка; молока нет, альтернативное молоко не предлагается.

Билет и книга подписывают «Шот 1/2» (`stepLabels`). Бабл ти: шарики кладутся после шейкера (`boba` рисуется на дне стакана), сироп стоит после заварки.

## Терпение и очередь (`src/game/patience.ts`)

- **Формула:** `patienceMax = (A_type + K_type · estimatedPrepSeconds(order)) · random · pace · cozy · helper · newbie`. A: regular 60, student 70, hurry 35; K: 1,6 / 1,8 / 1,0; `random` 0,85–1,25 на гостя (в игре `Math.random`, в модели и тестах — сидированный `rng`); pace 1,5/1/0,75, зал ×1,15, помощник ×1,2. Считается в `spawn()` (`04-customers.js`), когда заказ уже известен.
- **`estimatedPrepSeconds(order)`:** шаги `buildTasks` (двойной эспрессо и 0,4/0,6 л — два цикла) × `STEP_SECONDS` (около 10 с на шаг, из реального замера) + `ORDER_OVERHEAD_SECONDS` 11 с. Та же оценка — время игрока в `playerModel.ts` (`· speed` профиля), а в статистике смены `profile.speed = готовка / оценка`.
- **newbie** (`newbieFactor(day)`): день 1 ×1,4, день 2 ×1,3, день 3 ×1,2, дни 4–5 ×1,1, дальше ×1.
- **Строгая очередь** (сознательное изменение управления): заказ берётся только у первого гостя (`queueOrder(D.customers)`, порядок прихода; `notFirst(c)` в `04-customers.js` показывает «Сначала обслужите первого гостя» не чаще раза в 2,2 с и больше ничего не делает). Места `SLOTS` уже идут по порядку, остальные сдвигаются при уходе первого (`reindex`).
- **Терпение в очереди:** `queueDecayRate(position)` = 1 / 0,5 / 0,3 (первый, второй, третий+; `QUEUE_DECAY`); считается в `tickDay` (`05-day.js`) по индексу в `D.customers`, накопленное остаётся, меняется только скорость; перемножается с хинтом дня 1 (×0,3 в баре) и `SBX.noPat`. Помощник по-прежнему берёт простые заказы сам (очередь его не ограничивает).
- **Закрытие кафе:** гости приходят до 18:00 (`D.t < DAY_LEN`); после `D.closing` новых нет, очередь и бар дообслуживаются по обычным правилам терпения (принудительного ухода нет, «последнего заказа» нет). Страховка `CLOSING_LIMIT` = 240 с после закрытия завершает день через `endDay()` без штрафа (`lost` и рейтинг не меняются, заказ в баре возвращается один раз). В HUD после закрытия на чипе часов «18:00» стоит пометка «закрыто». Модель (`playerModel.ts`) устроена так же; сценарий `e2e/closing_flow.js`.
- **Реальные смены владельца** лежат в `data/real-shifts.json` (статистика с песочницы `#dev`, профиль «Средний», «Как у типичного игрока», ×1): это калибровка скорости профилей, не тесты.
- **Расходы смены (`costs`)** списываются при начале заказа (`barOpen` → `spend`), в том числе у гостей, которые ушли, пока их готовили: аномальные 702 ₽ при одном обслуженном — шесть начатых и брошенных заказов, это задумано, не баг учёта.
- Числа подбираются в `scripts/shop-sim.test.ts` (`SIM=1`): цель — «Средний» ранг 4 к дню 9–10 и ранг 9 минимум в 40 из 60 прогонов, «Уверенный» ранг 9 к дню ≤ 40, без застрявших. После изменений: `npm run sim:table`.

## Тесты: что и когда запускать

- Юнит-тесты (`npm run check`) после каждого изменения: логика в `src/game` должна быть закрыта ими.
- e2e запускаем только после изменений, которые трогают порядок гостей, заказ и приготовление, деньги и расходы, магазин, обучение, сохранения; целиком один раз перед крупным выпуском. Не гонять всё подряд после мелочей.
- Новые e2e писать только для денег, очереди, магазина и обучения; остальное закрывать юнит-тестами.
- e2e не входят в деплой, пока не станут стабильными: нестабильный сценарий не должен блокировать публикацию.
- Скриншотные и замерные скрипты (`*_shot`, `seq_shot`, `perf3`, `fps`) это инструменты для глаз, а не тесты.
- Нельзя ослаблять проверку ради зелёного результата: если ожидание устарело, обнови его на точное новое значение и пойми, откуда оно взято.
- Периодически проводить ревизию e2e: объединять пересекающиеся и удалять дублирующие.

## Работа с git

- Работа ведётся локально одним разработчиком: перед началом достаточно `git status`; в конце этапа push в `main` (или только коммиты, если владелец так сказал).
- Работаем только в ветке `main`, новые ветки не создаём. Владелец работает и локально, и в облаке; один запуск уже ушёл в чужую ветку, поэтому правило жёсткое.
- Начало: `git fetch origin`, `git status` (грязное дерево — остановиться и сообщить), `git pull --rebase origin main`. Конец: `git push origin main`. Никогда `--force`.
- Push вернул 403: `git format-patch -1 --stdout > out/<имя>.patch` и сообщить путь к файлу.
- `.gitignore` исключает `*.png`: для новой папки со скриншотами всегда добавляй исключение (так же было в Н1-3 и Б1-1).
- Репозиторий: https://github.com/mentanicarli/cuppable (раньше `chofix-game`). Игра называется Cuppable (латиницей, всегда с заглавной C); историческое «chofix» осталось только в ключах localStorage и именах файлов данных.
- Push в `main` запускает workflow «Deploy to GitHub Pages»: `check` и `lint:legacy`, затем публикация. Красный `check` = деплоя не будет.

## Проверка в браузере (e2e)

Каталог `e2e/` — наши Playwright-скрипты (не часть сборки). Установка: `cd e2e && npm install && npx playwright install chromium`. Свой Chromium: переменная `CHROMIUM=/путь/к/chromium`.

Как они работают: берут **отладочную сборку** (`npm run build:debug`, файл `dist/artifact.html`), подменяют строку запуска `newGame(); updateHud(); showTitle();` на такую же плюс `window.__dbg = { G, D, BR, … }` и дальше кликают мышью как игрок. Запуск: `node e2e/bar_test2.js dist/artifact.html out latte`.

- `menu_flow.js` — сценарий меню: титул → настройки → новая игра → пауза → музыка выкл → в главное меню → продолжить, экспорт/импорт/сброс, битое сохранение (`BASE=http://localhost:4173/ node e2e/menu_flow.js out/menu`, лучше с `HASH='#nopixi-lowfx'`); `music_test.js` — плеер на коротких тихих треках (кроссфейд, порядок);
- `visual_fixes_test.js` — кольцо фокуса меню, сидящий гость за ноутбуком (3 гостя × 5 состояний), гости без просветов (27 образов, разрешение 1 и 0,5, стоя и в ходьбе) и порядок слоёв досок пола; `SEED=…` для `seq_shot.js` задаёт случайные числа;
- `world_shot.js <html> <png>` — скриншоты титула и зала (проверка отрисовки Pixi);
- `bar_shot.js <html> <png>` — скриншот бара со всеми улучшениями;
- `bar_test2.js <html> <префикс> <ключ[:размер][,ключ[:размер]…]>` — полный заказ по шагам билета (любое число шотов, раф с эспрессо в питчер): помол → темпер → шот → вода/молоко/сливки → пар → заливка → подача; несколько заказов подряд в одном прогоне (`espresso2,cappuccino:0.4,raf:0.2`); цели берёт из `BR.rc`; печатает `served N -> N+1 money M` и `NO_ERRORS`;
- `milk_flow.js` — магазин по рангам и обучение молоку (день 1 → ранг 2 → покупка → первые 5 гостей → первый латте с карточкой и шагами → второй латте без подсказок → «Пропустить»), `BASE=http://localhost:4173 HASH='#nopixi-lowfx' node e2e/milk_flow.js dist/artifact.html out/milk`;
- `sandbox_flow.js` — песочница (`#dev`): без `#dev` кнопки и панели нет; день 10 / ранг 5 / «Все открыто» → заказ через панель → подача → «Закончить день»; сейв и настройки не меняются (`node e2e/sandbox_flow.js dist/artifact.html out/sbx`);
- `food_test.js`, `menu_test.js` (новые напитки; переменная `HASH` меняет хэш), `helper_test.js` (помощник);
- `empty_shot.js`, `fps.js`, `perf3.js` — сравнение скриншотов и замеры.

Старт новой игры в тестах — `require('./pw').startNew(p)` (титул → «Новая игра» → «Открыть кофейню»). Клики по карточке меню делай не раньше чем через ~0,7 с после показа: пока она «выезжает», Playwright может прокрутить страницу на 8 px.

Правила прогона: хэш `#nopixi-lowfx` для стабильности; на машине без GPU Pixi очень медленный — не пугайся 0,7–5 fps; запускай **по одному тесту** в фоне с таймаутом; не используй `pkill -f` со своими строками. Суммы денег в сидированных прогонах зависят от тайминга (плавают ±5 %), поэтому критерий успеха — «заказ завершён + NO_ERRORS + served 1», а не точная сумма. Старые эталоны денег (эспрессо 612 и т. д.) после правки экономики устарели.

## Известные нюансы и ловушки

- **Отладочная сборка для e2e:** переменная `CUPPABLE_DEBUG=1` нужна обоим шагам, иначе стартовая строка для e2e-хука не находится (`window.__dbg` не появится): `CUPPABLE_DEBUG=1 npx vite build && CUPPABLE_DEBUG=1 node scripts/fragment.mjs` (на Linux `npm run build:debug` ставит её только первому шагу; в Windows cmd не работает вовсе). Windows PowerShell: `$env:CUPPABLE_DEBUG=1; npx vite build; node scripts/fragment.mjs`.
- e2e-тесты: `BASE=http://localhost:4173` (после `npx vite preview --port 4173`) гонит их через http, звуки грузятся; все печатают `NO_ERRORS` (pageerror, console.error и warning, кроме шума GL). ## Как работать с владельцем

Владелец ведёт обсуждение и пишет промпты в чате claude.ai, а реализацию отдаёт сюда. Типичный запрос — список из нескольких пунктов; делай всё сразу, в конце — короткий отчёт: что сделано, что проверено, что **не** проверено, одно предложение «что дальше». Не спрашивай разрешений на очевидное; спрашивай, только когда решение необратимо и допускает два прочтения.
